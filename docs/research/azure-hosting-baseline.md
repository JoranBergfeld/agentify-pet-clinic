# Azure Hosting Baseline for the Workshop Starter

Research for [Identify the Azure hosting baseline for the workshop starter](https://github.com/JoranBergfeld/agentify-pet-clinic/issues/14), verified against official Azure documentation on 2026-08-11.

## Recommendation

Use **Azure App Service for Linux with the Java SE runtime** and a pre-authored `azd` template.

The starter repository should deploy the Spring Boot executable JAR directly to App Service and provision a Microsoft Foundry resource separately. Attendees run `azd up`; they do not run `azd init`, author Bicep, build containers, or choose Azure services.

## Why App Service

- The same executable JAR runs locally and in Azure.
- No Dockerfile, container registry, Kubernetes concepts, or buildpack behavior is required.
- A continuously available App Service instance avoids scale-to-zero cold starts during a short workshop.
- App Service supports system-assigned managed identity and ordinary application settings.
- The `azure.yaml` schema supports `host: appservice`.
- The infrastructure can be authored once and committed to the starter repository.

This requires more maintainer work than `azd init`, whose current code-detection workflow generates Azure Container Apps infrastructure only. That trade-off is acceptable because Azure is an execution environment rather than a learning objective.

## Alternatives

### Azure Container Apps

Container Apps is the only host currently generated by the `azd init` code-detection workflow. It supports Java source, JAR, and container deployment, but JAR deployment and several Java optimizations remain preview features. The default scale-to-zero behavior introduces cold starts; keeping a replica warm reduces the cost advantage. Container packaging, resource-provider registration, and environment behavior add workshop complexity.

### Azure Spring Apps

Do not use Azure Spring Apps. It entered retirement on 2025-03-17, is closed to new customers, and retires fully on 2028-03-31. Microsoft recommends Azure Container Apps or AKS for migrations.

### AKS

AKS is far beyond the infrastructure and operational scope of this workshop.

## Starter infrastructure shape

The committed `azd` template should provision:

- One resource group per attendee environment.
- A Linux App Service plan on a small, continuously available SKU.
- One Java SE App Service with a system-assigned managed identity.
- One Foundry resource using `Microsoft.CognitiveServices/accounts` with `kind: AIServices`.
- One chat model deployment using `Microsoft.CognitiveServices/accounts/deployments`.
- Application settings for the OpenAI-compatible endpoint and deployment name.
- The minimum role assignments required by the final authentication design.

The App Service build and deployment path packages the application with the Maven wrapper and deploys the resulting executable JAR.

## Decisions intentionally deferred

[Document the Azure permission and cost envelope](https://github.com/JoranBergfeld/agentify-pet-clinic/issues/12) must determine and verify:

- Target region and fallback region.
- App Service SKU and current regional price.
- Foundry model, `GlobalStandard` versus `DataZoneStandard` deployment type, quota, and current token prices.
- Whether the Spring AI OpenAI client uses managed identity directly or a secret stored through an approved Azure configuration mechanism.
- Exact built-in roles and resource-provider registrations required by `azd up`.
- Pre-work deployment duration assumptions.
- Reliable evidence that all chargeable and soft-deleted resources are removed after cleanup.
